# 2026-09-14 Work Log

## Email audit — password-reset OTP still landing in Gmail spam (PixelHouse / lankalens.online)

**Reported:** Gmail spam placement with SPF PASS, DKIM PASS (`d=lankalens.online`, `s=brevo2`),
DMARC PASS, Return-Path `bounces-…@send.lankalens.online`, SMTP IP `77.32.148.27`;
message also carries `List-Unsubscribe`, `List-Unsubscribe-Post`, `Feedback-ID`,
`X-CSA-Complaints` and a Brevo open pixel at `r.send.lankalens.online/tr/op/…`.

**Findings (code side — clean):**
- `server/routes.js` sends resets through `sendOtpEmail()` → `server/mailer.js`, which only
  uses `POST https://api.brevo.com/v3/smtp/email` (transactional) or the Brevo SMTP relay.
  Nothing calls the campaign API or Brevo lists; recipients are not Brevo contacts.
- Nothing in `server/`, `js/`, `api/` sets `List-Unsubscribe`, tracking options, or
  campaign/unsubscribe features — so those headers are injected by Brevo, not by this app.
- OTP content was already compliant: brand, code, 15-minute expiry, "ignore it" line,
  no links/images/marketing copy, text+HTML both sent.
- Sending IP reverse DNS = `ha.d.sender-sib.com` → Brevo infrastructure, no rogue relay.

**Findings (Brevo side — the actual answer):**
- Brevo adds the list-unsubscribe header to **every** message, campaigns *and*
  transactional (Brevo help: mandatory; transactional emails are exempt from an
  unsubscribe *link* in the body but not from the header). Not removable from code.
  Only Brevo Support can swap it for a `List-Help` header — Enterprise plan,
  recipient-triggered transactional mail with no promotional content (our case).
- Open/click tracking: no per-message switch in the v3 API or SMTP relay. Documented
  levers are (a) `contactPixelTrackingConsent` per recipient on the API (requires
  Brevo → Settings → Contacts → Per-contact pixel tracking consent = Yes), (b) Brevo
  Support disabling transactional tracking account-wide, or (c) "Anonymous email
  tracking" which anonymises but keeps the pixel.
- DNS audited read-only: SPF `spf.brevo.com` + `spf.privateemail.com`, `send.` subdomain
  SPF `-all`, DKIM only `brevo2._domainkey`, DMARC `p=none; rua=mailto:rua@dmarc.brevo.com`,
  MX privateemail. **All correct — deliberately left untouched** (per request).

**Changes made:**
- `server/mailer.js`: new `BREVO_PIXEL_TRACKING_CONSENT` env var (unset = unchanged
  behaviour; `off` = send `contactPixelTrackingConsent: false` on every transactional API
  recipient), Brevo `tags` on both transactional API sends (`password-reset-otp`,
  `order-confirmation`), `brevo_pixel_tracking_consent` added to `describeConfig()`.
- `server/index.js`: startup log line about tracking mode; warns that the flag does nothing
  on the SMTP transport (API-only lever).
- `EMAIL-DELIVERABILITY.md`: replaced the outdated/incorrect DNS guidance (it listed
  `_spf.sendinblue.com` and `mail._domainkey`, neither of which exist for this account) with
  the audited live records, added the code-side vs Brevo-side ownership table, the exact
  Brevo dashboard/support steps, and the Postmaster Tools recommendation.
- `README.md`: documented the new variable and the Brevo-injected headers.

**Verified:** stub-fetch test (payload with/without the consent field, tags, From/Reply-To,
text+HTML, subject) and stub-nodemailer test for the SMTP path (unchanged, no injected
headers); live `GET /api/email/status` returns the new field.

**Not done on purpose:** no DNS changes, no header faking, no removal of
`List-Unsubscribe` (that would be tampering), no "workaround" for a Brevo-side behaviour.
